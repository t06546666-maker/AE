# Counter Staff checkout

Merchant: More → Counter Staff (also the merchant menu). Create a named staff account with a mobile number and temporary password of at least eight characters including an uppercase letter. A number identifies one Counter Staff account across AE. Passwords are scrypt-hashed and never returned. Resetting or disabling access revokes existing sessions immediately. Staff change the temporary password on first login. Staff login is below Merchant Login; returning staff open the Counter Staff portal automatically.

The merchant sets the points-per-₹100 rate, redemption percentage/flat discount and minimum bill, then enables Counter Staff checkout. It is OFF by default. Existing flat-discount tiers and point caps remain enforced. A customer scanning an enabled shop QR enters their bill amount. Staff receive the shop-only request, check the actual bill, then confirm, return with a reason, or cancel with a reason. The customer can correct and resubmit a returned amount; revisions prevent stale confirmations. Return/cancel never calls checkout and does not change balances.

Confirmation calls the existing idempotent checkout service with the stored customer amount and owner-rule snapshot. It applies the existing purchase/points/redemption behavior and sends the customer’s bill, with payment left pending. Staff cannot set cash/paid, change rates, view CRM, view reports or edit owner settings. Amount confirmation is NOT proof of payment receipt. Uncertain/failed checkout stays locked for merchant review; never re-submit it blindly. Simultaneous decisions claim a request transactionally, so only one checkout executes.

Merchant activity includes staff name, customer, original/revised bill, discount, payable, points, decision/reason, time and purchase reference. A started confirmation or cancelled/returned request shows a preview, not applied points. Successful history keeps payment receipt unconfirmed by staff. Account creation/reset/access/rule changes are audited too. Staff account credentials and audit are server-only in Firestore; production rules were read and verified to deny all client reads/writes. Financial records remain in the existing Supabase checkout engine. No production balances or account records were created during testing.

Collections: ae_counter_staff, ae_counter_settings, ae_counter_activity/{merchant}/events, ae_counter_login_attempts. Uses existing ae_shop_requests and ae_shop_request_locks. JWT signing uses a domain-separated derivation of COUNTER_STAFF_JWT_SECRET or existing CUSTOMER_JWT_SECRET (32+ characters); the staff token is scoped to counter endpoints and is not a merchant/customer token. Login attempts are limited server-side. The dedicated staff client clears any prior main-app session when switching roles. Native push registers only after first password change; disabled staff receive no new request push. Browser sessions use foreground polling.

Rollout: build and review the website first. Ship an updated Android AAB before enabling any shop: old installed customer/staff assets do not have these screens. An older client receives an actionable amount-required response at an enabled shop; the existing merchant-scans-customer-QR path remains available. No SQL migration or new paid service is required. Do not enable a real shop or create real staff accounts during validation without selecting the intended shop.

## Product lists and merchant alerts

Counter Staff has Checkout requests and Product lists tabs. Staff access only their shop's Admin-approved product lists, with customer names, list text, pickup time and short-lived photo links. Confirmed, In progress, Order ready and Rejected use the same guarded transitions as merchant fulfilment. Staff cannot approve pending Admin reviews or access CRM, customer phone numbers, reports or owner settings. A Firestore audit intent is saved before a staff status update; a saved decision records staff attribution and notifies the merchant and owning customer. Duplicate decisions do not resend alerts.

Merchants receive new product-list arrival alerts while Admin review remains pending, a further review-ready alert after approval, new Counter Staff checkout requests, corrected amounts, returns, cancellations and uncertain outcomes requiring review. Existing purchase/payment notifications remain in place. Notification work is scheduled after a successful product-list submission so delivery latency cannot block the submitted result. Push delivery still requires valid device registration and enabled OS notification permission. No SQL migration is required: product lists remain in Supabase and staff audit/device registrations remain in Firestore. Installed apps need the new Android build for the Product lists tab.
Run node scripts/counter-local-demo.cjs and open http://127.0.0.1:3036/owner. This development-only server uses an in-memory mock database and a random per-process signing secret, never loads .env, and sends no real pushes. Preview controls switch between owner, staff and a simplified customer test panel; these controls are not part of the real staff app. Use Open demo staff or the sample login 9999999999 / CounterDemo1. Restarting the process clears demo data. Do not expose this preview outside localhost.


## Owner-away checkout mode

The merchant uses Who is handling checkout? → I am away — activate Counter Staff when leaving, and I am back — switch to Merchant on return. This changes only the saved checkout mode, preserving discount and point rules. New checkout-request pushes are exclusive: active Counter Staff while mode is on; merchant while mode is off. Staff see no checkout queue and cannot confirm when mode is off. Staff account access remains a separate merchant-created login permission. Merchant activity, transaction-completion and product-list alerts remain available. Existing enabled staff accounts are unchanged.
